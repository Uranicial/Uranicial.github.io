引言

本人平时一直在捣鼓各种个人项目，也参与实验室的团队项目，长期保持着随心所欲编写 Commit Message 的优良传统

然而，近期在维护个人博客及其他项目时，翻看过去的提交记录，发现连自己都已经搞不清楚当时究竟修改了些什么

于是鄙人痛定思痛，决定整理一份 Git 提交规范，既作为个人开发的参考，也方便今后的团队协作

主流提交规范

目前常见的 Git 提交规范及提交风格主要有以下几种：

规范 提交示例 特点
Conventional Commits feat(auth): add login 标准化程度高，适合自动化
Angular Convention fix(core): resolve crash 约束更加严格，强调模块与正文
Gitmoji ✨ Add login feature 使用 Emoji 标识提交类型
Git 传统风格 Add login feature 简单直接，侧重自然语言描述
混合规范 ✨ feat(auth): add login 兼顾可读性与结构化，但需要适配工具

其中，Conventional Commits（约定式提交）是一种应用广泛的提交规范，具有结构清晰、易于理解、便于自动化处理等特点，适用于个人项目及团队协作

Git 本身并不强制采用某种提交规范，同时不同项目团队之间的提交规范也可能不同

一套良好的 Commit 规范主要解决以下问题：

  • 统一团队成员的提交信息格式
  • 快速识别每次提交的目的和影响范围
  • 提高代码审查（Code Review）的效率
  • 自动生成更新日志（CHANGELOG）
  • 配合语义化版本（SemVer）实现自动版本管理和发布
  • 方便后续定位问题、回滚代码和追溯历史

Conventional Commits（约定式提交）

Conventional Commits (约定式提交)基于Angular提交信息准则，提供了更加通用、简洁和灵活的提交规范，并便于自动化工具解析，从而实现更新日志生成、语义化版本管理及自动化发布等功能

基本格式

  • Type:提交类型（必填）

  • Scope:影响范围（可选）

  • !:不兼容变更标记（可选）

  • Description:简短描述（必填）

  • Body:详细描述（可选）

  • Footer:附加信息（可选）

提交示例

Type (提交类型)

这是整套提交规范中最重要的部分，以下是 Conventional Commits 及其常见扩展所采用的类型：

Type 含义 适用场景
feat 新功能 新增功能、页面、接口
fix 修复缺陷 修复 Bug、异常、错误逻辑
docs 文档变更 修改 README、开发文档
style 代码格式 缩进、空格、分号调整
refactor 代码重构 不改变功能的代码结构调整
perf 性能优化 优化运行速度、内存占用
test 测试相关 新增或修改测试代码
build 构建相关 Gradle、Maven、依赖管理
ci 持续集成 GitHub Actions、CI/CD 配置
chore 日常维护 杂项配置、辅助工具维护
revert 回退提交 撤销之前的 Commit

需要注意的是，Conventional Commits 官方规范明确规定了 feat 和 fix 的语义，其他类型是被广泛采用的扩展，并非全部由官方强制规定

其他可选扩展类型

团队也可以根据业务需求增加如下类型

但不建议一开始引入过多扩展类型，类型之间可能产生语义重叠，增加团队成员判断成本

例如，deps 可以归入 build，hotfix 可以归入 fix，不一定需要单独定义

Type 含义
init 项目初始化
release 发布新版本
deps 依赖更新
hotfix 紧急修复
security 安全相关修复
i18n 国际化与本地化
ui 界面及视觉调整
config 配置文件修改
assets 图片、字体等资源变更
wip 尚未完成的开发工作
remove 删除功能或文件

Scope（影响范围）

Scope 用于描述本次提交涉及的模块、组件或者业务范围

Scope 没有统一的取值标准，通常由项目自行定义，建议与项目模块结构或业务划分保持一致

以一个 Android 应用项目为例

Scope 影响范围
auth 用户认证
ui 用户界面
home 首页模块
database 数据库模块
network 网络请求
api 接口模块
settings 设置模块
navigation 页面导航
gradle Gradle 构建
deps 项目依赖
readme README 文档
workflow 自动化工作流

实际提交示例:

Description（简短描述）

这里建议采用以下规则：

  • 使用动词原形开头，例如 add、fix、update
  • 英文描述首字母小写
  • 结尾不添加句号
  • 准确描述本次提交的实际变更
  • 尽量将标题控制在 50～72 个字符以内

其中，Git 项目自身将 50 个字符作为软限制，并推荐使用祈使语气、不在标题末尾添加句号

附上常用英文动词：

动词 含义 动词 含义
add 添加 remove 删除
update 更新 rename 重命名
fix 修复 replace 替换
improve 改进 optimize 优化
implement 实现 simplify 简化
enable 启用 disable 禁用
upgrade 升级 extract 提取
support 支持 migrate 迁移

Body（详细描述）

对于比较复杂的提交，可以在标题下方空一行，描述修改原因、具体内容及影响

Body 应重点说明 为什么修改、修改了什么、产生什么影响，而不是简单重复标题

Footer（附加信息）

Footer 通常用于关联 Issue、标识贡献者和声明不兼容变更

GitHub 支持通过特定关键字关联 Issue，在相应提交进入默认分支等满足条件的情况下自动关闭 Issue

其中 Refs 通常只用于引用，不表示自动关闭

Breaking Change（破坏性变更）

如果修改导致旧版本的接口或使用方式不再兼容，可以使用 ! 或 BREAKING CHANGE 标记，也可以同时使用两者

例如删除旧接口、修改公共函数参数、改变不兼容的数据格式等

容易混淆的提交类型

实际操作 推荐类型
新增一个页面 feat
修改页面的视觉样式 feat 或自定义 ui
调整代码缩进 style
修复页面显示异常 fix
重新封装一个组件 refactor
减少页面加载时间 perf
升级 Kotlin、Gradle build
修改 GitHub Actions ci
修改 .gitignore chore
修改 README docs
删除无用代码 refactor
删除已有业务功能 feat，不兼容时标记 !
撤销之前的提交 revert

特别注意：style 指的是代码格式，而不是 UI 样式。

Commit 与语义化版本（SemVer）

Conventional Commits 的重要优势是可以与语义化版本管理结合

Semantic Versioning（简称 SemVer，语义化版本）是一套由 Tom Preston-Werner 提出的软件版本命名规范，旨在通过统一的版本号格式及递增规则，明确不同版本之间的功能变化与兼容性关系

提交行为规范

同时，除了对提交信息的格式进行约束之外，本人也建议对提交行为本身进行规范

原子化提交（Atomic Commit） 是其中一个重要原则，即每次提交应当围绕一个明确且相对独立的目标展开

如果一次修改包含多个彼此独立的任务，例如新增功能、修复缺陷和调整代码格式，则应尽可能将其拆分为多个独立提交

需要注意的是，原子化提交并不意味着一次提交只能修改一个文件或模块。只要这些修改服务于同一个目标，就可以包含在同一次提交中

此外，应避免将密码、API Key、临时文件及不需要纳入版本控制的构建产物提交至仓库。提交前应检查实际变更，并尽可能保证每次提交均处于可构建、可测试的状态

结语

Git 提交规范的意义并不在于增加开发过程中的形式主义，而在于通过相对统一的约定，使代码变更更容易被理解、追溯和维护

对于个人项目而言，规范的提交信息能够帮助未来的自己快速理解过去的修改；对于团队项目而言，则有助于降低沟通成本，提高代码审查和协作效率

当然，提交规范并非一成不变。不同项目可以根据自身需求制定合适的提交类型、影响范围及自动化流程，没有必要为了遵循某种规范而引入过于复杂的约束

规范应当服务于开发，而不是成为开发的负担

至于本人，希望今后翻看自己的 Git 提交记录时，不必再靠猜测来理解过去的自己究竟干了些什么
